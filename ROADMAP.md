# LCM-X roadmap

Status: reconciled 2026-10-19. v0.28.0 is the current stable release (2026-10-18). v0.28.1 (a patch for the v0.28.0 follow-ups) and v0.29.0 (agentic memory, the evidence release) are next. The [vision](VISION.md) says what we are building and why. Issue [#658](https://github.com/electricsheephq/lcm-x/issues/658) is the tracker; GitHub milestones hold the issues for each release. The current stable release is recorded in [docs/project-status.md](docs/project-status.md).

## How releases work

- **One themed minor about every two weeks, by gate.** Each minor has one theme and a written "GA accepts when" line. Work runs in parallel lanes; a feature ships in the first release after it passes its own gate, so dates are forecasts.
- **Proven quality ships on.** A feature becomes the default when a pre-declared, paired measurement on held-out questions, read by a frontier model, shows a significant gain in evidence or answer quality, and it holds the lossless and wait bars. Token cost is not a gate ([vision](VISION.md)). Scope freezes at the first release candidate. After the third candidate, a minor ships only with known, non-blocking items; otherwise the failing change is taken out.
- **Patches only for release-blocking defects reachable in real deployments:** data loss, duplicate rows, a wedged or reset session, a request over the context window, or a security defect such as a secret exposure or an access-control bypass. At most one patch a week unless an incident is live.
- **Behaviour and default changes ship only in minors.** v0.24.9 was scoped before this policy was written; it is the last release under the old rule.
- **The release after v0.27.0 was v0.28.0.** The v0.27.0 release notes call it v0.27.1. It shipped as a minor because it adds off-by-default features and fixes defects that were triaged as not release-blocking. The dependency and the default change once planned for it moved to v0.29.0 (#1186).
- **Every release candidate runs the gauntlet** in [bench/specs/RELEASE-READINESS-V1.md](bench/specs/RELEASE-READINESS-V1.md). A candidate that fails is fixed and respun; only a candidate that passes can become GA, and the GA tree differs from it only by its release notes. v0.27.0 shipped with two disclosed release-manager exceptions (see its row). That is not a general waiver: #1305 proposes a narrow spec clause for those two cases only, and every other gate still has to pass.
- **Every release also carries a recall scorecard** ([#898](https://github.com/electricsheephq/lcm-x/issues/898)), first applied at v0.26.0:
  - **Every release candidate:** the configuration that candidate ships by default is scored as the gated row, with full-text recorded beside it when local semantic recall is the default. A local-semantic default must first meet its own A/A′ prerequisite in the release spec. It is scored on LongMemEval-M retrieval against the previous GA. It passes when no question's `lcm_recall` result changes. Otherwise each change must be traced to a named commit and judged intended. Net R@10 may not fall more than 0.005, and no category may fall more than 0.02.
  - **Recorded, not gating:** the non-default recall configurations and a cached Voyage tracker. The shipped default gates under the release spec; any other recorded row becomes a gate only through a spec change that names its pass rule.
  - **At the first release candidate of every release, major, minor or patch:** facts kept after compaction (Track S) are compared with the previous GA's row by an exact stratified run-level permutation test on identical material. Answer accuracy (LongMemEval-S, LoCoMo) uses its own paired rule. A later candidate re-runs both unless its diff touches only docs, tests, release notes, CHANGELOG.md and bench files outside the measurement kit, the kit is unchanged, and the shipped default recall configuration is unchanged.
  - Comparisons with other compaction systems are reported as H1 evidence, not per-release gates.

## H1 — compaction you don't notice

Every compaction LCM-X starts runs on the turn thread, so the user waits for it. v0.24.9 bounded that wait. v0.25.0 met its bar: on the gauntlet's live soak, compaction ran at p90 55.5 s with the longest at 72.1 s. Compaction breaks the prompt cache; additional breaks from stub swaps are tracked in #788 and have not been isolated. H1 removes the wait in steps.

### Compaction architecture: four layers

The leading systems no longer rely on one lossy summary. They stack four layers, and this is LCM-X's compaction architecture (decided 2026-10-10, tracked in [#658](https://github.com/electricsheephq/lcm-x/issues/658)):

| Layer | What it does | LCM-X | Work |
|---|---|---|---|
| 1. Clear old tool output first | Replace large or old tool results with durable references before summarising | Large-output externalization and active-replay stubbing (first sight above 10k tokens; aged tier above 2k tokens outside the fresh tail) | On by default in v0.27.0 (#1013; the default flip is #1070) |
| 2. Summary | Summarise what is compacted | The summary DAG; the summariser sees the middle of long messages (#611) | v0.27.0; the prompt-v2 flip rule in #660 |
| 3. Deterministic re-insertion | Put back what must not be lost: the user's own words, instructions, plan | The objective survives assembly overflow (#1048); the LCM note reaches the model (#900); the user carry packet (#659); an identifier index (#1066). The host rebuilds the system prompt and re-inserts the todo list. | #659: Eval-2 was inconclusive (#1064), so the decision moves to v0.31.0 with invisible compaction, at a larger sample; #1066 |
| 4. Lossless, searchable history | Let the agent recover anything exactly | `lcm_recall`, `lcm_grep`, `lcm_expand` and `lcm_describe` over the lossless store; stemmed full-text recall (#1035); local semantic recall for managed deployments (#1014, #1063) | v0.27.0 |

**Why layer 3 comes first.** On Track S (checkpoint 304, LCM-X v0.24.8 against Codex native compaction), Codex kept 132/132 facts stated by the user against LCM-X's 75/132, and 27/72 facts from the middle of long tool outputs against 0/72. LCM-X was ahead on assistant facts (+20) and on the head and tail of tool outputs (+21). The Codex arm was read by a different reader model in that run.
- The tool-middle gap starts at the summariser input clip, which #611 addresses: 42/72 middle facts now reach leaf summaries, up from 0/72. That is a leaf-level result; whether those facts survive rollups and assembly for the same reader is measured end to end by Eval-2.
- The user-fact gap is the missing verbatim user carry; #611 does not change it. In an offline screen with the same reader, the carry packet raised user-row facts by 50.8 points with no losses (#659). Eval-2 decides ([#1064](https://github.com/electricsheephq/lcm-x/issues/1064)).

**Never below Hermes built-in.**
- Hermes's built-in compressor keeps user messages verbatim, an identifier index, a recovery footer and stubs for old tool results.
- When LCM-X is the context engine it replaces that compressor. The floor is measured, not assumed: LCM-X must score at least as well as Hermes built-in on every fact class, read by the same reader in Eval-2's Hermes built-in arm (#1064).
- v0.27.0 records that comparison; v0.31.0 gates on it. Layer 1 (#1070) and the objective and LCM-note parts of layer 3 (#1048, #900) ship in v0.27.0. The user carry packet (#659) ships when Eval-2 keeps it. The identifier index (#1066) ships only if Eval-2 measures a gain.

**Deferred, with revisit triggers.**
- **Summary-free compaction**, where the model writes notes and a fresh window starts. Revisit if a provider enables it for a generally available model; LCM-X's layer 4 already provides the history tool that design depends on.
- **Delegating the active-window summary to provider-native compaction.** Revisit after coexistence with Hermes native compaction is defined (#1068) and an Eval-2 arm shows a gain.
- **Turn-relevant evidence injection.** Revisit when the pre-answer arm passes its pre-declared bar.

## H2 — memory that wins (now)

Where LCM-X stands (2026-10-19):

- **Shared-reader board (OmniMemEval).** On 2026-10-18 we ran LCM-X v0.28.0-rc1 on OmniMemEval's harness, which runs every system with one gpt-4.1-mini reader and one gpt-4o-mini judge. Local semantic recall was on, with 20 hits per question. These rows are self-run: the board has not accepted them yet, and our adapter is under review upstream (MemTensor/OmniMemEval#11). Per-question outputs, a script that recomputes every cell from them, and a manifest of commits, settings, commands and hashes are published as the [evidence release](https://github.com/electricsheephq/OmniMemEval/releases/tag/lcmx-v0.28.0-results-20261018).

  | BEAM-100K | 71.84 | 1st of 12 reproduced rows, tied with the next three | two self-run entries score higher (75.07, 72.61) |

- **Inside Hermes, against its built-in compressor** (100 LongMemEval questions, one reader, 2026-10-10): LCM-X with local semantic recall 79, Hermes built-in 78, no difference. With pre-answer evidence LCM-X scores 89 (p = .027), with a higher p90 answer time (#1111).
- **Agent Memory Leaderboard.** LCM-X v0.28.0 is entered in the Open-source Methods division of the Agent Memory Leaderboard Cycle 2 Textual track. It is scored and in the organisers' review. The result is published with the official board. The coding track runs in the same division before the cycle closes.
- **LongMemEval-S with a frontier reader.** 85.8% for v0.26.1 with local semantic recall and 72.2% without embeddings (reader gpt-6.1-sol, the benchmark's gpt-4o judge). A frontier model given the full history and no memory system scores 92%.

- **Not entered yet:** BEAM 10M, DolphinBench, LifeBench, and LongMemEval-M answer rows.
- **What others report.** Leading systems self-report 92–96% on LongMemEval-S. On OmniMemEval, two systems that self-report about 94 score 72 and 56.

Where we lose, ranked by measured size (each issue holds the evidence):

1. **Evidence that never reaches the reader.** In a string-match recount, the gold evidence is missing from the delivered hits in about three quarters of LoCoMo misses and half of LongMemEval-S misses. LoCoMo multi-hop questions score 66.3 (11th of 15). On LongMemEval-S multi-session questions, recall finds the right sessions but misses the turn. Recall stops at 25 hits. On the OmniMemEval LoCoMo board we deliver about 1,700 tokens per question, against about 5,400 and 24,700 for two leading systems. Work: delivery depth (#1607), reranking (#1187), within-session depth and session breadth (#1188), sender provenance (#995).
2. **Event ordering.** BEAM-100K event ordering scores 25.2; nothing enumerates the matching events and puts them in time order (#1589).
3. **Superseded facts.** HaluMem dynamic update scores 62.8. Step 0 rejected the delivery-only slice: the newer update was never delivered in 36 of 67 misses, and only 4 had both states delivered. Source-linked superseded facts (#1590) stay with #1191 in v0.30.0.
4. **Abstention.** HaluMem memory boundary scores 89.7, 9th of 13 (#1591).
5. **The shipped default.** Without embeddings, LongMemEval-S drops from 85.8% to 72.2% (#1186, #1586).
6. **Compaction.** Facts kept after compaction have stayed near 0.78 since v0.27.0. The user's standing task was paraphrased in 2 of 6 v0.28.0-rc1 runs (#1592). The turn still waits for foreground compaction: p90 45–56 s on the gauntlet cells (#1123).
7. **Integrity.** The nightly reliability matrix passes its gate while cells outside it fail (#1588). External users reproduced a compaction wedge on v0.28.0 (#1162). v0.28.1 adds diagnostics; offline reconstruction for affected stores is #1598 (v0.29.0).

The plan:
1. **Evidence delivery first (v0.29.0).** One pass of screens, declared in advance and run on frozen candidate pools from a development split, picks the bets. The order:
   1. delivery depth step 1, retrieval only (#1607): done, passed;
   2. delivery depth step 2, held-out answers (#1607);
   3. the time-order slice (#1589), screened at the depth step 2 chooses and only when BEAM event coverage there is above 40%, because the ordering score cannot exceed coverage;
   4. rerank on the chosen pool (#1187);
   5. within-session depth and breadth (#1188);
   6. sender and role (#995).

   Only winners land. Every delivery change carries no-loss guards on abstention, adversarial and knowledge-update questions, degraded recalls (#1591, #1609) and recall latency (measured with #1586's instrument). The development split overlaps the board sets, so a board rerun after these choices reports the held-out score beside the total.
