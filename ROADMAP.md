Status: reconciled 2026-10-28 (roadmap v4). [v0.29.0](https://github.com/electricsheephq/lcm-x/releases/tag/v0.29.0) (local semantic recall on by default) is the current stable release, at `c13dea3783bdbd1aab52d83dff5d009bfade0bd2`. The next release is the v0.29.1 patch (v0.29.0 follow-ups). After it, the order is: nothing lost (v0.30.0), compaction you don't notice (v0.31.0), facts that update (v0.32.0), then Claude Code (v0.33.0) and more harnesses (v0.34.0). The [vision](VISION.md) says what we are building and why. Issue [#658](https://github.com/electricsheephq/lcm-x/issues/658) is the tracker; GitHub milestones hold the issues for each release, and bench, kit and CI work sits in the continuous **Instruments and process** milestone, each item dated by the release that needs it. The release-process changes are tracked in [#1995](https://github.com/electricsheephq/lcm-x/issues/1995). The current stable release is recorded in [docs/project-status.md](docs/project-status.md).

## How releases work

- **One themed minor about every two weeks, by gate.** Each minor has one theme and a written "GA accepts when" line. Work runs in parallel lanes; a feature ships in the first release after it passes its own gate.
- **Dates are ceilings, not schedules.** Each release's date means "no later than". A release ships as soon as its gate passes, even well before its date, and the next theme starts at once. Scope is never added to fill time. A date at risk is protected by moving P3 issues out first. A failed invariant is never moved: the release respins with the smallest fix that passes the same gate, or its claim is revised.
- **Issue caps.** A release milestone holds at most about 45 issues and 8 at P0 or P1. An issue enters a milestone only with a measured bar or a reproduced defect; P3 issues not merged by the first release candidate go to the backlog.
- **Backlog reporting** (from v0.29.1). Each week reports the breakage queue beside total open issues and the 28-day created/closed ratio. The queue is a fixed rule: open and (data-integrity, or P0, or a P1 bug outside **Instruments and process**), plus a versioned list of named exceptions. If relabels alone move it by more than 3 in a week, the rule is fixed before it is used as a headline. Every inflow ratio states its basis: as of 2026-10-28, issues were opened about 3.3 times as fast as release-milestone issues were completed, and 1.7 to 1.85 times as fast as all issues were closed.
- **Proven quality ships on.** A feature becomes the default when a pre-declared, paired measurement on held-out questions, read by a frontier model, shows a significant gain in evidence or answer quality, and it holds the lossless and wait bars. Token cost is not a gate ([vision](VISION.md)). Scope freezes at the first release candidate. After the third candidate, a minor ships only with known, non-blocking items; otherwise the failing change is taken out.
- **Patches only for release-blocking defects reachable in real deployments:** data loss, duplicate rows, a wedged or reset session, a request over the context window, or a security defect such as a secret exposure or an access-control bypass. At most one patch a week unless an incident is live.
- **Behaviour and default changes ship only in minors.** v0.24.9 was scoped before this policy was written; it is the last release under the old rule.
- **The release after v0.27.0 was v0.28.0.** The v0.27.0 release notes call it v0.27.1. It shipped as a minor because it adds off-by-default features and fixes defects that were triaged as not release-blocking. The dependency and the default change once planned for it moved to v0.29.0 (#1186).
- **Every release candidate runs the gauntlet** in [bench/specs/RELEASE-READINESS-V1.md](bench/specs/RELEASE-READINESS-V1.md). A candidate that fails is fixed and respun; only a candidate that passes can become GA, and the GA tree differs from it only by its release notes. v0.27.0 shipped with two disclosed release-manager exceptions (see its row). That is not a general waiver: #1305 proposes a narrow spec clause for those two cases only, and every other gate still has to pass.
- **The gauntlet is tiered for patch releases from v0.29.1 and for every release from v0.31.0** ([#1995](https://github.com/electricsheephq/lcm-x/issues/1995)), through amendments to the release spec ([#1997](https://github.com/electricsheephq/lcm-x/pull/1997), [#2008](https://github.com/electricsheephq/lcm-x/pull/2008)). The minors v0.29.0 and v0.30.0 run all phases. Every candidate runs Phase B, the required CI checks, the live soak, the reference-agent window (D5) and the roundtrip. Each release also runs the rows behind its own gate, and the remaining rows run weekly on main. Before v0.31.0 there is no weekly run on main, so a patch release's unselected rows are not run, and its release notes list them as not run. A change promotes the rows for the surface it touches: ingest, storage or retry changes promote Phase A, D1 and D4/D8; compaction or summariser changes promote D2/D3 and D7; recall or delivery changes promote D1 and D4/D8; host-integration changes promote Phase C. The full tier runs at least every third minor and at every default flip. v0.30.0 runs the full tier.
- **Every score-sensitive change also runs on a maximum configuration** (a cloud embedding model; the ablation in [#1963](https://github.com/electricsheephq/lcm-x/issues/1963)) and must not lose there: the lower 95% bound of the paired difference must stay above −2 points. A win on the default configuration alone is recorded as an experiment, not adopted. Latency and cost claims for a default use the release spec's reference-machine fixture; if that fixture cannot run, the change ships off by default.
- **Every release also carries a recall scorecard** ([#898](https://github.com/electricsheephq/lcm-x/issues/898)), first applied at v0.26.0:
  - **Every release candidate:** the configuration that candidate ships by default is scored as the gated row, with full-text recorded beside it when local semantic recall is the default. A local-semantic default must first meet its own A/A′ prerequisite in the release spec. It is scored on LongMemEval-M retrieval against the previous GA. It passes when no question's `lcm_recall` result changes. Otherwise each change must be traced to a named commit and judged intended. Net R@10 may not fall more than 0.005, and no category may fall more than 0.02.
  - **Recorded, not gating:** the non-default recall configurations and a cached Voyage tracker. The shipped default gates under the release spec; any other recorded row becomes a gate only through a spec change that names its pass rule.
  - **Under the tiers** (patch releases from v0.29.1, every release from v0.31.0), the release spec's tier selection replaces the every-candidate and first-candidate cadences in this list: a row runs in a candidate only when that candidate selects it.
  - **At the first release candidate of every release, major, minor or patch:** facts kept after compaction (Track S) are compared with the previous GA's row by an exact stratified run-level permutation test on identical material. Answer accuracy (LongMemEval-S, LoCoMo) uses its own paired rule. A later candidate re-runs both unless its diff touches only docs, tests, release notes, CHANGELOG.md and bench files outside the measurement kit, the kit is unchanged, and the shipped default recall configuration is unchanged.
  - Comparisons with other compaction systems are reported as H1 evidence, not per-release gates.

## H1 — compaction you don't notice

Every compaction LCM-X starts runs on the turn thread, so the user waits for it. v0.24.9 bounded that wait. v0.25.0 met its bar: on the gauntlet's live soak, compaction ran at p90 55.5 s with the longest at 72.1 s. Compaction breaks the prompt cache; additional breaks from stub swaps are tracked in #788 and have not been isolated. H1 removes the wait in steps.

### Compaction architecture: four layers

The leading systems no longer rely on one lossy summary. They stack four layers, and this is LCM-X's compaction architecture (decided 2026-10-10, tracked in [#658](https://github.com/electricsheephq/lcm-x/issues/658)):

| Layer | What it does | LCM-X | Work |
|---|---|---|---|
| 1. Clear old tool output first | Replace large or old tool results with durable references before summarising | Large-output externalization and active-replay stubbing (first sight above 10k tokens; aged tier above 2k tokens outside the fresh tail) | On by default in v0.27.0 (#1013; the default flip is #1070) |
| 2. Summary | Summarise what is compacted | The summary DAG; the summariser sees the middle of long messages (#611) | v0.27.0; the prompt-v2 flip rule in #660 |
| 3. Deterministic re-insertion | Put back what must not be lost: the user's own words, instructions, plan | The objective survives assembly overflow (#1048); the LCM note reaches the model (#900); the user carry packet (#659); an identifier index (#1066). The host rebuilds the system prompt and re-inserts the todo list. | #659: Eval-2 was inconclusive (#1064), so the decision moves to v0.31.0 with invisible compaction, at a larger sample; #1066 |
| 4. Lossless, searchable history | Let the agent recover anything exactly | `lcm_recall`, `lcm_grep`, `lcm_expand` and `lcm_describe` over the lossless store; stemmed full-text recall (#1035); local semantic recall for managed deployments (#1014, #1063) | v0.27.0 |

**Why layer 3 comes first.** On Track S (checkpoint 304, LCM-X v0.24.8 against Codex native compaction), Codex kept 132/132 facts stated by the user against LCM-X's 75/132, and 27/72 facts from the middle of long tool outputs against 0/72. LCM-X was ahead on assistant facts (+20) and on the head and tail of tool outputs (+21). The Codex arm was read by a different reader model in that run.
- The tool-middle gap starts at the summariser input clip, which #611 addresses: 42/72 middle facts now reach leaf summaries, up from 0/72. That is a leaf-level result; whether those facts survive rollups and assembly for the same reader is measured end to end by Eval-2.
- The user-fact gap is the missing verbatim user carry; #611 does not change it. In an offline screen with the same reader, the carry packet raised user-row facts by 50.8 points with no losses (#659). Eval-2 decides ([#1064](https://github.com/electricsheephq/lcm-x/issues/1064)).

**Never below Hermes built-in.**
- Hermes's built-in compressor keeps user messages verbatim, an identifier index, a recovery footer and stubs for old tool results.
- When LCM-X is the context engine it replaces that compressor. The floor is measured, not assumed: LCM-X must score at least as well as Hermes built-in on every fact class, read by the same reader.
- Eval-2 (#1064) closed in v0.27.0 with no scored Hermes built-in arm, so the gate moves to the head-to-head in [#1595](https://github.com/electricsheephq/lcm-x/issues/1595), with a per-fact-class non-inferiority margin declared before the run. v0.31.0 gates on it. Layer 1 (#1070) and the objective and LCM-note parts of layer 3 (#1048, #900) ship in v0.27.0. The user carry packet (#659) ships when Eval-2 keeps it. The identifier index (#1066) ships only if Eval-2 measures a gain.

**Deferred, with revisit triggers.**
- **Summary-free compaction**, where the model writes notes and a fresh window starts. Revisit if a provider enables it for a generally available model; LCM-X's layer 4 already provides the history tool that design depends on.
- **Delegating the active-window summary to provider-native compaction.** Revisit after coexistence with Hermes native compaction is defined (#1068) and an Eval-2 arm shows a gain.
- **Turn-relevant evidence injection.** Revisit when the pre-answer arm passes its pre-declared bar.

A head-to-head on the current release (LCM-X as shipped, Codex native, lossless-claw and Hermes built-in, one reader for every arm) runs in the v0.31.0 cycle ([#1595](https://github.com/electricsheephq/lcm-x/issues/1595)). Where we lose, ranked by measured size (each issue holds the evidence):

1. **Evidence that never reaches the reader.** In a string-match recount, the gold evidence is missing from the delivered hits in about three quarters of LoCoMo misses and half of LongMemEval-S misses. LoCoMo multi-hop questions score 66.3 (11th of 15). On LongMemEval-S multi-session questions, recall finds the right sessions but misses the turn. Recall stops at 25 hits. On the OmniMemEval LoCoMo board we deliver about 1,700 tokens per question, against about 5,400 and 24,700 for two leading systems. Work: delivery depth (#1607), reranking (#1187), within-session depth and session breadth (#1188), sender provenance (#995).
2. **Event ordering.** BEAM-100K event ordering scores 25.2; nothing enumerates the matching events and puts them in time order (#1589, v0.31.0).
3. **Superseded facts.** HaluMem dynamic update scores 62.8. Step 0 rejected the delivery-only slice: the newer update was never delivered in 36 of 67 misses, and only 4 had both states delivered. Source-linked superseded facts (#1590) move with #1191 to v0.32.0.
4. **Abstention.** HaluMem memory boundary scores 89.7, 9th of 13 (#1591).
5. **The shipped default.** Without embeddings, LongMemEval-S drops from 85.8% to 72.2%. Local semantic recall is on by default from v0.29.0 (#1186, #1586).
6. **Compaction.** Facts kept after compaction have stayed near 0.78 since v0.27.0. The user's standing task was paraphrased in 2 of 6 v0.28.0-rc1 runs (#1592). The turn still waits for foreground compaction: p90 45–56 s on the gauntlet cells (#1123, v0.31.0).
7. **Integrity.** The nightly reliability matrix passes its gate while cells outside it fail (#1588). External users reproduced a compaction wedge on v0.28.0 (#1162). v0.28.1 adds diagnostics; offline reconstruction for affected stores is #1598 (v0.31.0). Retry, replay and restart shapes are the largest open family of loss and duplicate defects; v0.30.0 is dedicated to them (#1993). Compaction can also stop forming leaves on a normal tool-heavy session (#1998, fixed in v0.29.2), stall after a warm engine re-ingests its stored prefix (#1961, v0.30.0), or keep failing to publish in a multi-profile gateway (#1555, v0.31.0).

The plan:
1. **Delivery and abstention are one paired bet.** A change that delivers more evidence than declared behaviour ships with a sufficiency signal (#1591), or after its own check on unanswerable questions passes. Both go through one paired gate. The defect fix restoring declared delivery (PR #1679) and duplicate-hit collapse (#1681) ship in v0.29.0. Delivery depth (#1607) is v0.30.0's evidence item.

   Depth and breadth (#1188) selected no default after their declared screens; rerank (#1187) also selected none. Both are re-screened in v0.32.0 with the sufficiency signal and speaker names. Every delivery change keeps its abstention, adversarial, knowledge-update, degraded-recall and latency guards (#1591, #1609, #1586).
2. **Gate on what customers run.** From v0.29.0, local semantic recall (bge-small, on the user's machine) is the default and the release-gate arm; embeddings off is recorded beside it (#1186). The default model is re-chosen by measurement on the reference machine (an Apple M-series laptop with 16 GB). In the v0.29.0 screen (#1715), four larger models recalled 1.6–2.9 points more turns, but none fit the ~4 GB memory budget with its vectors, so bge-small stays. Reduced-precision builds of the two closest challengers are measured next, gated on answer rows (#1715).
3. **Facts that update (v0.32.0).** Write-time extraction (#1191) with source-linked superseded facts (#1590) and the entity foundation (#1862). Full timeline assembly and time order (#1589) ship in v0.31.0, and replay identity repair (#1674) in v0.30.0.
4. **Measure before tuning.**
   - A ≤30-minute development loop is a kill/futility screen: it only sees large effects. A nightly factorial run on ≥400 clustered questions promotes; an untouched cohort confirms. Delivery, sufficiency and embeddings are measured together.
   - Every screen gets a power check before it is commissioned. No bar the baseline cannot meet. Measure the noise floor (the same configuration twice) and a second judge before using ±2-point bars. The development split overlaps the benchmark sets, so a benchmark rerun after a development-split choice reports the held-out score beside the total.
   - **Frontier-model rows (#1189):** frontier readers, two frontier judges from different families on the same blinded answers, published prompts, question ids and configurations, and a same-reader full-context baseline. Agentic and single-retrieval rows stay in separate tables.
   - **Shared-reader boards:** OmniMemEval (BEAM 10M [accepted upstream on 2026-10-26](https://github.com/MemTensor/OmniMemEval/blob/8d1ff33904abccbcdef9363cf8ae82fc97574b26/docs/user_memory/results.md#result-summary): 63.32, 1st of 12 reproduced backends; the other rows were accepted upstream on 2026-10-21), DolphinBench (run inside Hermes), LifeBench and LongMemEval-V2. LongMemEval-M answer rows are judged by frontier models.
   - **Recall QA target:** ≥90% on LongMemEval-S and LoCoMo (non-adversarial) under the matched public protocol. A rank is claimed only on matched rows that hold under a second judge.
   - **Bench honesty:** two corrections to the LoCoMo/LongMemEval gate adapter are in flight: conversation speaker names were not kept (other adapters in the same harness keep them), and summary nodes carried no source lineage. Each correction lands with a paired old-vs-new adapter row on a fixed product release. Earlier gate rows stay as recorded and are compared only with rows from the same adapter.
   - Results are published in the repository scoreboard with tokens per query and cost (#898, #1067).
5. **Which benchmarks matter, and how we enter them.**
   - **Headline rows use the shipped default.** Board entries are run with the configuration a new user gets (local bge-small today). Where a board accepts it, a second row labelled "max configuration" (a cloud embedding model such as Voyage) is added beside it, never in place of it. A design change counts only if it helps the default row and shows no loss on the max row under the maximum-configuration rule above (lower 95% bound of the paired difference above −2 points).
   - **Priority order:** our own release instruments (they gate every release) first. Then agentic memory inside a real harness (AML coding, the in-Hermes head-to-head), BEAM and LongMemEval, where the target is first place. Then PersonaMem, which is expected to move with entity memory (v0.32.0). HaluMem is kept as a guard against wrong or stale answers. LoCoMo is kept for comparability with published systems, not as a design target: it is short, older, and rewards retrieval tuning that does not carry to long agent sessions.
   - **Embedding ablation** (#1963, after v0.29.0): off, local default, best local, and a cloud model on BEAM-100K, LongMemEval-S, LoCoMo and PersonaMem with one shared reader, compared pairwise (McNemar). It shows how much of each score comes from the embedding model and how much from LCM-X itself.
   - **Our own benchmark** (#1964; the Hermes part runs alongside v0.30.0, and a Claude Code row joins with v0.33.0's adapter; the published board does not gate a release): long agent sessions inside real harnesses, with code and text first. Questions need facts across many compactions, superseded decisions, and exact constraints. Images, audio and screen recordings come later, with H4. It is designed to be hard for every system, including ours, and is published with its harness, so others can run it.
6. **Lead on long-session continuity.** Nothing lost, operative facts and constraints kept exactly across compactions, and a small visible wait. Generated sessions run to deep compaction (600+ checkpoints, nested summaries); current Codex, Claude Code and Hermes built-in are measured under the same instrument and published (#1595, #1587). This is the leadership target, not a claim that it has been met.
7. **Showcase.** After each release or benchmark result, the README, the project site and the results page are updated from the same data. Every number links to its receipt and says what it measures.
8. **Outside designs** go into a research queue (#1150).
9. **Deferred past v0.34.0:** non-English recall (#1047 records a CJK recall timeout). Multimodal memory stays research: images are opt-in per profile, and capture streams start with one measured use before any schema (#1719). **Conditional:** forgetting a stored memory on request (#1171) ships in v0.32.0 only off by default, only if its condition holds, and only as a confirmed retraction; the store stays lossless.

Milestone: **H2 — memory that measurably wins**.

## H3 — one memory, any harness

- **Architecture.** Context assembly and compaction stay inside the host process. A memory service serves recall to other harnesses through an MCP endpoint (ingestion from other harnesses with v0.34.0). Each store has one writer, and events keep a stable identity across hosts.
- **First pair:** Hermes and Claude Code, with portable session export (v0.33.0).
- **Next:** Codex, OpenClaw and Cursor (v0.34.0).
- **Also in H3:**
  - teams and multi-agent use;
  - query views (#694);
  - proactive recall (#962, #969, #865).

## H4 — memory for agents in the world (research)

Events with time, place and modality, for agents and robots that act over days. One measured use comes before any schema commitment.

The memory layer already needs no cloud.
