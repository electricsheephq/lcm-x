- Fix: When the host changes its list before the ingest cursor, moved tool-call rows and their results are now stored within a presence window of 10,000 stored rows, 20 million bytes of stored text (including tool-call text) and 10,000 stored tool-call entries, across the session, its verified compression ancestors and its recorded rotation predecessors (all three limits must hold) (#2455). Tool ids match exactly, including non-ASCII ids; an id stored anywhere in that scope counts as stored; a new call is stored only with the results the view shows for it, and a new result only with its call; a reused id (#2172) keeps main's result. The window is sized in SQL before any row loads and the audit loads no payload file, so its added wait under the write lock stays within 150 ms at each limit (measured on a 14-core machine at load below 7). The limit is logged at INFO once per session per process. Past the window, these rows stay positional replays as on main, a named loss limit to be fixed in v0.30.x (#2467). A replaced reply (#2116) is not covered here and moves to v0.30.x (#2467). If a presence read fails, ancestry cannot be verified with state.db present, or a rotation predecessor write failed in this process, the audit keeps its own finds, leaves the other rows as replays and logs a warning.
- Known limit (#2463): where the ancestry only looks complete (no state.db, or a state.db missing the child or parent row) and a predecessor record was never written in an earlier process (including a write that failed there), missing ancestry can still cause carried rows to be stored again.
