## 1. The one sentence that matters

**We do not yet know whether our memory system is good.**

That is not pessimism, it is today's measurement result. Here is everything we can actually defend:

| claim | status |
|---|---|
| our memory makes an agent **22% faster** (−56.3s/q, p<0.0001, 48/60 questions) | **established** |
| our memory improves **accuracy** | **withdrawn** — McNemar null across 3 paired arms (p=0.727/1.000/0.774) |
| our memory reduces **tokens** | **not established** — +3.2%, CI spans zero |
| our memory **compresses** a large corpus | **not ours** — the coding agent does this, vanilla included |
| our memory **retrieves better at scale** | **never tested** — both banked results used trivially small corpora |

We have one real, narrow advantage, measured on a benchmark that does not need a memory system. Everything
that would make us "best on market" is unmeasured. **The strategic priority is therefore not to improve the
product — it is to find out what the product does.** You cannot optimise what you have never measured.

### 1b. UPDATE, same day (F27 + F28) — one row of that table is now settled, and it sharpens the phase order

`retrieves better at scale` is still **never tested** — that is Phase 1. But a *different* question got answered
for free: **what our layer contributes on V1-small is now measured, and it is at its ceiling.**

- retrieval: **100% any-gold, 97.2% all-golds** (486/500)
- evidence representation: failures get **more** gold evidence than passes — no crowding-out
- evidence structure: the renderer already groups by session and dates every item
- **52 of the 56 failures had the COMPLETE gold evidence in the prompt**

So on V1-small roughly **90% of the remaining 11.2-point gap belongs to the reader's synthesis, not to us**
(≈0.8 pts retrieval · ≈2.8 pts abstention calibration · ≈7.6 pts model reasoning). A presentation mechanism aimed
at it was specced and then **withdrawn unrun** when its premise failed (F28).

**Why this makes the phase order more right, not less.** It closes the tempting side-quest. V1-small was always
the benchmark "that does not need a memory system" — now we can say so with numbers instead of intuition, and we
know that grinding it further buys at most ~3 points and probably fewer. **The thesis can only be tested where the
corpus stops being grep-exhaustible**, which is exactly Phase 1 (#159) and the medium tier (#161).

## 2. Why we were flying blind (the actual root cause)

Not compute, not ideas, not effort. **Measurement.** Today we ran four arms and could read none of them:

- **Underpowered slices.** A random 60q slice holds ~17 abstention questions, so an abstention mechanism was
  tested on 17 samples — the effect we produced (+23.5 pts) reads p=0.219. Invisible by construction.
- **Unpaired comparisons.** Our headline claim compared a 451-question run to a 60-question run.
- **Untested scale.** V2 small = 100 trajectories shared by all 451 questions. V1 = 514 messages in an
  isolated per-question store. Both exhaustible by `grep`.
- **Silent artifacts.** A store that held exactly the small tier's 200 trajectories. A dispatch packet naming
  a repo without provider pinning. A `per_question.jsonl` read while the judge was still writing it.

**Every one produced clean, plausible, wrong numbers. Nothing errored.** That is the failure mode to engineer
against, and it is the real content of the owner's "foundation so you can run autonomously."

## 3. The path — three phases, in strict order

### PHASE 1 — Find out if we have a product (days, not weeks)
**Single-store V1 at 389x** is the decisive experiment and costs nothing: re-ingest the V1 data we already
hold as ONE store (51 → 19,829 sessions; 514 → 199,641 messages), same 500 questions, same gold answers,
direct before/after against the banked 444/500.

Three outcomes, all actionable:
- **accuracy holds + latency flat** → we have the product claim: *your memory can grow without your queries
  getting slower or dumber.* That is the market-differentiating statement, and it is exactly where the
  competition (agent greps a folder; stuff a 1M context window) breaks.
- **accuracy holds + latency grows** → we are an index that doesn't scale. Fixable engineering, known target.
- **accuracy FALLS** → our retrieval does not survive distractors. **This is the outcome we most need to know
  and currently cannot see.** It would be the single most valuable finding of the program.

Run the **file-scan arm alongside it**: at 199,641 messages a coding agent's brute force should break. That
comparison is the honest version of the one that embarrassed us today.

### PHASE 2 — Build the loop that makes wrong conclusions hard (the "foundation")
This is what the owner is asking for, and today defined its requirements precisely. Five components:

1. **Scale-first by default.** Every mechanism evaluated at ≥2 corpus sizes. Memory systems are defined by
   behaviour under growth; a single-scale result is not evidence about a memory system.
2. **Auto-powered slices.** Given a mechanism's target class, generate the slice that can *see* it (all 128
   abstention questions, not 17) and refuse to run an underpowered gate. Today's biggest waste, mechanised away.
3. **Paired-by-default scoring.** McNemar + discordant counts + provider-error accounting computed
   automatically. A headline percentage delta should be hard to produce without its paired test attached.
4. **Dual-consumer.** Weak fixed reader (leaderboard) *and* frontier reader (product truth) on the same packs
   — cheap, since curation is the shared expensive stage. Ship rule: helps both → default-on; leaderboard-only
   or product-harmful → config-gated off; product-only → ship anyway, that is the business.
5. **Regression suite.** Every banked result re-runnable on demand, so a change that silently breaks a prior
   number is caught. We came within one decision of destroying the reproducibility of every small-tier number
   by extending a store and shifting corpus IDF.

**This is the highest-leverage engineering in the program** — not because eval infrastructure is glamorous,
but because it converts a day that yields four unreadable arms into a day that yields one trustworthy answer.
It is the precondition for autonomy: an agent running unattended must not be able to fool itself.

### PHASE 3 — Then compete, on the axes that are real
Once Phase 1 says what we have and Phase 2 makes results trustworthy:
- **Latency and cost at scale** — our measured strength, on frontier consumers, where customers live.
- **The leaderboard as marketing, not as the goal.** V2 `medium` is worth submitting (official, lower bars,
  two arms we already own would score non-zero) but it is a *credibility* play. It cannot demonstrate our
  architecture: it pre-solves candidate selection and locks a deprecated weak reader.
- **Publish our own scaling benchmark** — including the negative attribution honestly (the agent does the
  compression; on a 100-file pool vanilla equals us). A benchmark we publish that is *fair to competitors* is
  worth more than a leaderboard slot, and it is the artifact that defines the category we want to win.

## 4. Positioning, stated honestly
We are an **agent enhancer**, and today's attribution supports that precisely: the agent does the reasoning
and the compression; we make its memory access fast and cheap **at a scale where the alternatives fail**. The
competitor is not RAG. It is (a) an agent grepping a folder, and (b) stuffing a large context window. Both win
at small scale — which is why every result we have looks unimpressive, and why Phase 1 is the whole ballgame.

## 5. What I will not do
- Chase leaderboard points on a track that cannot show our value, while calling it product progress.
- Ship a mechanism default-on because it helps a weak reader, without checking the frontier consumer.
- Report a delta smaller than run-to-run spread as a finding. (Three claims died of this today.)
- Build Phase 2 tooling before Phase 1 tells us what to measure — the 389x run is cheap and answers first.
