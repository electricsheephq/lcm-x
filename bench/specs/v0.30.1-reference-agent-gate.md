# v0.30.1 reference-agent gate

GA requires the deciding checks on copies of the reference agent’s conversations and the live stand-in on the final install. The copy checks stand in for the D2/D3 compaction rows (D2 facts kept, D3 the Track S absolutes), which are reported as NOT RUN.

The gate passes only when every bar below passes. A failed bar means the gate has not passed. Missing or inconclusive evidence, or a required path that no pass exercised, also blocks GA: “not run” and “not exercised” never count as a pass. Evidence that is not bound to the measured tree does not count.

The gate owner runs this gate and rules on its stop questions. The release manager decides anything that changes the release. A failed bar, an unclassified item, or a case this sheet does not cover is a stop question. A stop question blocks GA until the gate owner rules on it. The gate owner takes it to the release manager when the ruling would change the release. A ruling can void a run for a harness fault and order a rerun, classify an item under a rule this sheet states, or take the item to the release manager. It cannot turn a failed bar into a pass.

Those statements now apply in full only to these checks, which protect stored data on the reference agent's install:
1. the reversibility item and its rollback copy cell. In that cell 8f8c881f runs ten passes on a copy the candidate has written, starting from the list the candidate last returned, beside a control arm that runs 8f8c881f on a copy the candidate never wrote. The cell passes when no stored row is lost or duplicated, under the loss and duplicate bars the gate record sets for it before its data (a skipped row shows as a row with no stored copy, a doubled row as a byte-equal copy), and when each recognition count (lineage marks, occurrence bindings, identity-anchor records) is no more than the control arm's. Two more kinds of stop question hold GA until they are ruled on:

- a fault in the indexed state that the reversibility item opens, found before that item runs: the one-time index build must close cleanly with the index in the schema, and the clone that the reversibility item opens must come from a source whose write-ahead log held no frames after that close, or had none.

Their failures, inconclusive results and missing evidence are stop questions that the gate owner rules on after GA. They do not hold GA, and a fix goes into a patch release. The live stop signs are unchanged.

On each run, the attribution step puts every row a harness cold bind stored, on the candidate and on its control in the same repeat, into one class: a turn row the harness appended, a re-store of an older row's tool calls, a version, a new row caused by a list row the store lacked, or unattributed. Report each class's count on both builds, and every unattributed row by store ID and content digest.
2. Match each unattributed candidate row to the control's unattributed rows, one to one. A row that existed before the clone matches by store ID and content digest. A row first stored during the cell matches as the list below matches new rows (role and payload digest), and the report gives both builds' store IDs. The content digest is that payload digest.
3. A row unattributed on both builds is an instrument limit: the harness limit that affects both builds alike, in the paragraph above. The report names it by store ID and content digest. An unattributed row read this way is not an unclassified item for the attribution, and the rerun rule below for rows a record cannot classify does not apply to it; the matching and order rules below still apply to it.

| Observation | Outcome |
|---|---|
| Both builds' attribution completed, every unattributed row has a content digest, and every unattributed candidate row has a match on the control (or there is none) | pass for that run; the attribution is complete for the paragraph above once every run of the cell has this outcome |
| Both builds' attribution completed, and an unattributed candidate row with a content digest has no match on the control | fail |
| Either build's attribution did not complete, or an unattributed row has no content digest | inconclusive: the attribution is not complete for the paragraph above, so its counts stay reported and do not block GA, as that paragraph says; the run's attribution is re-analysed, or the run is repeated |
| An unattributed control row with no match on the candidate | reported; it does not change this outcome, and the paragraph below on rows the control alone stores still applies to it |

When the rows of one run give different outcomes, the run is a fail if any row fails; otherwise it is inconclusive if any row is inconclusive.

Match and report cold-bind rows repeat by repeat on the same copy:
- Copies match by source row.
- Versions match by source row and payload digest.
- New rows match by role and payload digest, plus the tool-call ID or tool-calls identity where applicable.
- Rows that existed before the clone compare by store ID directly.
- Rows stored during the cell map through earlier matched binds, and relative order is checked on the mapped IDs.

The same rows under different new IDs pass, with the offset and its cause reported. A different relative order on the candidate is unclassified. A row that only the candidate stores fails. A byte-equal copy is the exception: it fails only once harness cold-bind copy counts gate, and until then it is reported. Fewer copies pass.

When the control alone stores a new row or version, the candidate must show durable evidence for that same occurrence. Its UID binding must resolve to a stored row with byte-equal payload; for a row without a UID, its list-row-to-store mapping must do so. A row present only in the returned list is not evidence, and neither is a byte-equal row bound to a different UID. Without that evidence it is a loss and the cell fails.

If a record cannot classify a row, rerun one repeat pair per conversation with both clones kept, and decide those rows. Apply that result only to other repeats that match class, source and size; decide the rest pair by pair. Keep every run’s clones until the cell is judged.

**Ingest after a pass.** Measure preflight ingest after each pass. Measure post-turn hook wall time after each pass, or at a bind where the recipe runs the hook. At load below 8, a candidate time over 25 s is a stop question if either holds:
- the matched control is at or below 25 s;
- the candidate is more than 5 s slower than the control.

Report all matched deltas, and report any slowdown over 5 s to the release manager. Split available ingest timings into lock wait, reconcile, store-ID mapping and identity-anchor backfill. Record whether a commit proof was found or the full reconcile ran, and record the load. The host hook has a 30 s limit; read it only where a host turn is run. This stop rule applies wherever an after-pass ingest is measured, including the ingest that follows the pass in the cold-start cells. The cold-start seconds themselves are reported, not barred.

**Timed evidence.** Run alone with 1-minute load under 8. Enable load protection for the cold-start timing runs, wait 30 s, and record whether it was active. If the required sample is still short, stop and send the valid and void counts to the gate owner; the sample is not extended automatically. Read content on all complete records regardless of load.

## Post-salvage rehearsals

Each rehearsal runs alone under the walk-load rules.

**Warm continuation.** On a fresh copy of the state after the seventh pass, cold-start the folded head as stored. Then run two warm passes with a 40 s stand-in, on the candidate and on 8f8c881f. Record leaf and frontier progress, holes, re-stores and placeholder versions. Each of these is a stop question:
- a hole line;
- a pass without a leaf;
- a frontier that does not move;
- a condensation that does not shrink the head;
- a pass over 480 s;
- a host refusal.

Re-stores in the known salvage shape, at no more than the control’s level, go in Known issues. A result worse than the installed build or v0.30.0 goes to the release manager.

**Crossing rehearsal.** On the candidate, start from the state after the seventh pass, on the corrected harness. Before any pass, the cold start must recognise the stored head. Its recognition reason and cursor must match the reference agent’s live bind on that state, or, where no live bind exists on it, what the corrected harness recorded for that state before the arm. If it does not, the arm predicts nothing: report it and stop. Rows the cold start stores beyond the new turn are reported, not a stop, under the rule for harness cold-bind copy counts. Use the reference agent’s settings, a 40 s stand-in and the host’s salvage-or-refuse function. Drive up to four passes to cross the second designated hole row. The crossing is shown when a pass that starts at or beyond the designated row ends beyond it and publishes a leaf. If the four passes do not show it, that is a stop question. Report the list rows freed by the first pass that starts strictly before the designated row and ends at or beyond it. Each of these is also a stop question:
- a hole line;
- a pass without a leaf;
- no frontier progress;
- a stall, timeout or reset;
- a survival-fit event;
- a pass over 480 s.

Report for each pass:
- the plugin’s count and the host’s estimate, in and out;
- the rows its leaves cover, with their hidden and copy shares;
- whether a condensation ran before or after the leaves;
- the visible tokens freed and the summary tokens added;
- the hole line and the frontier movement;
- on growth: the rows the salvage rewrote, the tool rows over 200 characters left, and the host function’s verdict.

State the two harness limits in the report: the host’s post-compaction steps are not applied before the estimate, and totals are per pass, not per leaf. Read each pass by the host’s estimate, allowing 2,000 tokens for the unapplied post-steps:
- Clear: the pass shrinks by at least 2,000 tokens.
- Undecided: a smaller shrink, or no change. A single undecided pass is reported. Two consecutive undecided passes are a stop question.
- Grows and the host function salvages it: this is the no-growth guard’s Known issue. It is reported.
- Refused by the host function: a stop question.

## Live stand-in for GA

Install v0.30.1-rc4 in a single recorded move, after the reversibility item, with the pre-install snapshot of both databases taken. On that install, all four conditions below must hold with 0 intervening stop signs.

1. The first live cold bind stores 0 byte-equal copies. Report versions of in-place edits separately.
2. Two automatic passes driven by the reference agent’s own traffic each publish a leaf with 0 content failures, 0 host refusals, 0 hole lines, 0 stalls, 0 timeouts and 0 condensations that fail to shrink the head.
3. The privacy re-embed completes and the user’s waits during it are reported.
4. After one idle gap of at least 600 s, the next turn’s rows are stored.

**First-hour prompt cache (dated 2026-11-21, rulings T1-460 and T1-461).** The read is reported. Only the stop question in the table below holds GA.
1. A turn is one user message and the agent's work on it, read from true turn boundaries. The host's API-call counter is not a turn boundary: it counts calls per agent object across turns.
2. A call rewrites when it writes more cache tokens than it reads, by the cache-write and cache-read token counts in its usage line in the reference agent's log. A turn has a rewrite when any of its calls rewrites. A turn with a call whose usage line lacks either count, and no call that rewrites, is unreadable.
3. A pass explains a rewrite in its own turn or in the next turn. A rewrite after an idle gap of 60 minutes or more is also explained. The start of each read counts as a pass.
4. The rule: between one pass and the next, at most one turn with a rewrite; and no two consecutive turns with a rewrite that no pass explains. Unreadable turns are skipped: two rewrites with only unreadable turns between them count as consecutive.
5. Read the rule on the first 60 minutes of turns on the install, and on 8f8c881f's last 24 hours before the move. The second read is the control. A read with no readable turn is unreadable; any other read is judged on its readable turns.

**Live stop signs.** From the move until all four conditions hold, each item below is a stop sign on a single occurrence. A stop sign blocks the stand-in until the gate owner rules on it. It goes to the release manager when the ruling would change the release. The two qualifying passes must come after the ruling.
- A row leaves the list with no byte-equal or fuller stored copy under a node in the returned head. One exception counts as pending summary: the host’s placeholder rewrite of a row above the frontier whose full text is stored.
- A coverage-by-ID flag that lasts more than two commits.
- A type error from the compaction call, or any LCM ingest failed event.
- The store held past 300 s while a turn waits.
- A pass over 480 s. Passes over 270 s are reported with their phase split.
- A provider rejection of an unpaired tool call, or a failed turn.
- Any survival-fit event: applied, dropped the summary prefix, could not fit, or skipped because the list holds rows not yet stored. Routine exit-fit skips are reported.
- Any host auto-reset of the main conversation, or a context-compression timeout.

Through the field period, each item on the live stop list is a stop question on a single occurrence. Report salvage, and any rise in the plugin’s count of the list.
